## 1. ⭐ 第一梯队（类型 A）：已承诺、但代码实测没有

### F1 · AED 实时地图（真的地图）　规模：**M**
- **承诺**：建议书 §04「**AED 实时地图** —— 精确显示周边 AED 位置与**开放状态**。"前往取 AED"一键触发责任人联动与导航」；§07 也以「自动识别最近可用 AED 并推送导航路线」为联动第一步。
- **实测现状（三处证据）**：
  1. **全仓无任何地图组件/SDK** —— grep `<map|createMapContext|leaflet|amap|AMap|mapbox` 在 `急救侠-uniapp/src` **零命中**（只有 `utils/location.ts` 的 `uni.getLocation`）。
  2. **新闻里的"地图卡"是 CSS 假图**：`pages/news/index.vue:107-119`，标记点用 `left: (30 + i*25)%` / `top: (20 + i*20)%` **按序号硬算位置**，**完全不用 lat/lng** ⇒ 纯装饰。
  3. **AED 侧是列表 + 跳系统地图**：`api/aed.ts:144` `fetchAedList(lat,lng)` 做距离排序列表；`stores/aed.ts:70` 用 `uni.openLocation` 交给系统地图 App。**应用内无地图、无"开放状态"可视化**。
- **缺口性质**：**这是建议书最显眼的旗舰承诺之一**，也是政府现场演示最容易被点开的功能。当前形态（列表 + 假图）**不足以支撑"实时地图"这一表述**。
- ✅ **好消息：数据层已经齐了，缺口纯在"渲染层"** —— `db.ts:105-132` 的 `aed_devices` **已有**：
  `lat` / `lng` / `distance`（地理坐标）、**`status`（默认 `'available'`）**、**`open_hours`**、`indoor` / `floor` / `finding_instructions`（找路信息）。
  ⇒ **F1 不需要任何迁移或 schema 变更，是纯前端展示层任务**，风险与成本都比看上去低。
- **要决定的事**：① 地图服务商 —— uni-app H5 ⇒ **高德 / 腾讯 JS SDK**（需申请 Key，**且有配额与商用授权问题**）或 **Leaflet + OSM 瓦片**（免 Key，但国内图源与合规需评估）；② 是否顺带把 `status`/`open_hours` 显示为"开放状态"（**建议要**，这是承诺原文的用词）。

### F2 · 中英双语界面（i18n）　规模：**M**　**状态：⏳ 进行中（P0-1 ~ P0-5 + **P1a 已完成**；P1b 待做，见 §8）**
- **承诺**：建议书 §05 旅游城市方案 ——「**国际旅客安全**：平台支持**中英双语界面**，SOS 呼救全程无需语言沟通，解决**语言障碍下的急救盲区**」。
- **实测现状**：全仓 grep `vue-i18n|useI18n|\$t\(|locale` **只命中 `lang="ts"` / `lang="scss"`**（属性名误命中）⇒ **完全没有 i18n 基建**，全部文案是硬编码中文。
- **缺口性质**：**"旅游城市"整条方案的卖点之一**。而且这是**架构级**改动（越晚做越贵）：23 个页面目录的硬编码文案都要抽 key。
- **要决定的事**：是否**只做"急救主链路"双语**（SOS / 急救指引 / AED 取用 / 免责确认 —— 覆盖承诺的真正场景），而非全站双语。**我建议只做主链路**：建议书的原话就是"SOS 呼救全程无需语言沟通"，范围小、收益直接。

### F3 · SOS 反滥用「可追溯」　规模：**S**（或改为改口径）　**状态：✅ 已完成（2026-09-14）**
- **承诺**：建议书 §10「触发 SOS 后系统**要求二次确认**，恶意虚假呼救行为**可追溯至账号实名信息**，并将依据相关行政法规向有关部门报告」。
- **实测现状**：`pages/rescue/index.vue:225-231` 的 import **只有组件与 utils，无任何 `@/api`** ⇒ **SOS/急救指引全链路纯本地**（语音指引 / 节拍器 / 本机拨 120 / 勾选式免责），**服务端无 SOS 记录**。（此前 `NEXT_STEPS.md` 的反滥用章节已独立得出同一结论。）
- **缺口性质**：⚠️ **这不是普通功能缺口，是"对外文件里的合规承诺"未落地**。两条路，**必须选一条**：
  - (a) **补服务端埋点**：SOS 触发时写一条最小事件（谁/何时/位置精度可降级），使"可追溯"成立；
  - (b) **改口径**：把建议书措辞从"可追溯至账号实名"改为"本机二次确认 + 免责确认"，并在下次提交版本中同步。
  - **不要**放着不管 —— 政府文件里的承诺落空比不承诺更伤。

### F4 · 志愿服务时长记录 + 官方志愿服务证明　规模：**M**
- **承诺**：建议书 §10「志愿者认证及任务记录**符合国家志愿服务时长记录标准**，可向**政府志愿服务平台同步数据**，志愿者可获得**官方志愿服务证明**」；§06 合作事项亦列入乙方职责。
- **实测现状**：grep `服务时长|志愿证明|志愿服务证明|serviceHours|volunteerHours|证明` 在 `src`（前后端，排除测试）**零命中** ⇒ 只有积分/勋章，**没有"时长"这一维度，也没有任何证明生成/导出/同步**。
- **缺口性质**：这是**志愿者长期留存与政府背书的关键**（建议书 §06 写明政府方职责是"提供荣誉证书、政府表彰"）—— 缺了"时长+证明"，志愿者的付出**无法转化成官方可认可的凭据**。
- **可复用现成能力**：`volunteer.ts` 已有积分/等级；`gov/dashboard` 的 CSV 导出已有 **BOM + RFC 4180 + 公式注入清洗**的成熟实现（见 `NEXT_STEPS.md` 技术债第 5 条与安全收敛段）⇒ **证明导出可照抄，不必重造**。

### F5 · 物理开锁 / IoT 网关对接
- **依据**：`aed-linkage-prd.md:226` 明写「❌ 本期不做：**物理开锁 / 电子锁 / IoT 网关对接**」；但契约已留位 —— `unlock_command_status`（`not_issued|issued|acked`，**未来** `dispatched`/`failed`）+ `unlock_token`（`aed-linkage-design.md:92`、`:396`）。

### F6 · 队籍核验（把 `affiliation` 从"自述"变"核验"）
- **依据**：`NEXT_STEPS.md` 安全收敛段记录 —— `affiliation='蓝天救援队'` 注册即得 **silver / 500 分 / 3 救援 / 3 证书**，**用户已裁定暂时保留**（按可信自述），并注明「**未来上线队籍核验再改审核授予**」。
- **缺口性质**：这是**已知的信任边界弱点**（自填队名即得等级与荣誉）。有政府或机构合作时，"队籍"就是可核验对象。
- **注意**：改动会**回收已发出的等级/分数** ⇒ 需明确的**存量数据策略**（这正是它被延后的原因）。

### F7 · 责任人信誉体系
- **依据**：`aed-linkage-prd.md:226` 本期不做项之一。
- **价值**：建议书 §07 把「责任人**响应确认**」作为核心指标（目标 **<2 分钟**）⇒ 有了响应数据，**"响应率/响应时长"的信誉画像**是自然下一步，且**能反哺政府看板**。
