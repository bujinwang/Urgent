# 数据出境合规 · 自检问卷（E2 · 境外机房的必办项）

> 生成：2026-09-19 ｜ 依据：`external-blockers.md` §2.1
> 背景：E2 机房选**中国境外** ⇒ **免 ICP 备案**，但急救侠处理**用户个人信息**（姓名、手机号、位置、救援记录）
> 属《个人信息保护法》下的**个人信息出境**，仍需合规评估。本问卷供**你 / 法务**照单作答，
> 结论决定部署架构（是否境内数据中转、脱敏/加密实现）。工程侧据此再立 F 项。
> ⚠️ 本文件是**自评清单**，非法律意见；最终路径以法务结论为准。

---

## 0. 为什么必须做（一句话）
境外机房 ≠ 免合规。个人信息出境走「标准合同备案 / 安全评估 / 认证」三选一，阈值看**数据类型 + 量级**。

## 2. 路径判定（法务结论后回填）

| 情形 | 路径 | 动作 |
|------|------|------|
| 出境达**安全评估**阈值（重要数据 / 大量个人信息） | **通过安全评估**（国家网信部门） | 走评估申报 |
| 一般个人信息、签标准合同 | **标准合同 + 备案**（网信部门） | 拟合同、备案 |
| 符合认证条件 | **个人信息保护认证** | 申请认证 |
| 出境合规成本过高 | **回退「中国大陆 + ICP 备案」** | 改 E2 步骤 1 另一分支 |

## 5. 建议答案（草案 · 2026-11-11 · 待法务复核，非法律意见）

> 目的：把上面 Q1–Q8 从「空白问卷」变成「建议 + 待确认」双列，你/法务只需**确认或纠正**，
> 不必从零作答。凡标「⚠️ 需你/法务拍板」的，工程侧无法代决。

### 5.1 实际出境 PII 清单（来自 `急救侠-server/src/db.ts` schema，非臆测）

| 数据 | 字段 | 表 | 敏感度 | 备注 |
|------|------|----|--------|------|
| 用户姓名 | `name` | users | 中 | 直接标识 |
| 手机号 | `phone`（迁移 038，可空） | users | **高** | 电话注册写入；微信用户为空 |
| 城市 | `city` | users | 低 | 仅到城市级（非 GPS） |
| 单位/组织 | `affiliation` | users | 低 | 可能暴露职业关联 |
| 头像 | `avatar` | users | 中 | 若为照片含人脸 |
| 资质证书 | `certifications`（JSON） | users | 低 | 急救证书编号，非健康数据 |
| AED 责任人姓名 | `custodian_name` | aed_devices | 中 | 设备级，非用户级 |
| AED 责任人手机 | `custodian_phone` | aed_devices | **高** | 设备级，非用户级 |
| 设备/任务地址 | `address` | aed_devices / tasks | 中 | 精确到门牌/点位 |
| 设备/任务坐标 | `lat`,`lng` | aed_devices / tasks | 中 | **设备/点位坐标，不是用户自身 GPS** |

**关键缓释点（务必写入法务说明）**：
- 用户自身精确位置**不采集** —— F1 设计 D1/T12 在 schema 层强制 `users` 表无经纬度列。出境 PII 不含"用户实时位置轨迹"。
- 当前 schema **不含用户健康/医疗史**（急救证书 ≠ 病历）。⚠️ 需你确认：rescue/任务记录里是否间接落入"行踪/健康"敏感类别（PIPL 第 28 条敏感个人信息口径）。

### 5.2 Q1–Q8 建议答案

| # | 建议答案 | ⚠️ 需你/法务拍板 |
|---|---------|----------------|
| Q1 境外地区 | **推荐新加坡**（数据保护法制成熟、对华低延迟、非大陆免 ICP）；次选**香港**（同免备案、近大陆）。两者皆可作主区。 | 最终落地区；是否双活/备份区 |
| Q2 出境数据类型 | 见 §5.1 清单：姓名、手机号(高)、城市、单位、头像、资质、设备责任人姓名/手机(高)、设备/任务地址与坐标。**不含用户 GPS、不含健康史**。 | 是否认同"无健康数据"口径；头像是否算人脸敏感信息 |
| Q3 量级 | 先假设**未达安全评估阈值**（一般个人信息，且敏感个人信息<10 万、总人数<100 万），走「标准合同+备案」档。 | **实际活跃用户 / 日出境条数**（Bert 填真实预估；量级决定阈值档） |
| Q4 境内留存 | **推荐：境内数据中转，境外仅拿脱敏/聚合结果**（最小化出境原则）。⚠️ 但境内公网接入层需 ICP —— 与"境外免备案"初衷冲突，需权衡。 | **架构抉择**：全量出境(简洁但合规重) vs 境内中转(合规轻但需 ICP)。法务定 |
| Q5 脱敏/加密 | 手机号/责任人手机**掩码**（中间 4 位 `*`）；地址**粗化至区/街道级**（不精确到门牌）；传输 TLS（DEPLOY.md 已默认）；静态加密（按结论补）；头像不存人脸特写。 | 掩码/粗化粒度是否达标；静态加密密钥管理方案 |
| Q6 接收方 | 境外接收方 = 急救侠**自身运营的境外实例/云商**（如 AWS SG / 阿里云国际），无第三方共享。标准合同 = 与云商签 DPA；若全量出境还需境内主体↔境外接收方标准合同。 | 境外运营主体是否独立法人（影响合同主体）；云商 DPA 条款 |
| Q7 告知同意 | 隐私政策 + **出境单独告知/单独同意** + 撤回入口。前端 i18n 文案已就绪（待补文案，见 §3 工程待办）。 | 同意文案定稿（中/英）；撤回入口交互 |
| Q8 留存/删除 | 用户资料留存至**账号注销 + 法定期限**；救援/任务记录按业务必要期（建议 ≤2 年）；删除走现有 `service:purge` / `sos:purge` 接口。 | 各数据类型具体留存期；是否需出境数据本地化删除证明 |

### 5.3 路径预判（依 §5.2 假设）

若 Q3 量级未达安全评估阈值、且 Q4 选**境内中转** ⇒ 大概率走 **标准合同 + 备案**（最轻路径）。
若 Q4 选**全量出境** ⇒ 仍走标准合同 + 备案，但需额外准备境内主体↔境外接收方合同与备案材料，合规负担更重。
**回退选项**：若法务判定出境成本/风险过高 ⇒ 改回「中国大陆 + ICP 备案」（external-blockers.md §2 另一分支）。
